# 可重複評測：速度與準確率

目的：每次調整斷句或顯示策略時，用**同一段、有標準答案**的音訊，比較速度與品質有沒有退步。一次只改一個變因。

## 1. 建立 FLEURS 評測素材（只需做一次）

```powershell
.venv-win\Scripts\python.exe windows\build_fleurs_eval.py --minutes 20
```

- 從 Hugging Face 下載 `google/fleurs`（CC BY 4.0）的英文測試集音訊與逐字稿，以及同一批句子的中文參考；第一次約需下載數百 MB，快取在 `.cache/fleurs/<commit>/`。
- **版本固定：** 先把 `main` 解析成一個 commit，三個檔案都用同一個 commit 下載，並把 commit 與每個檔案的 SHA-256 寫進 `.reference.json`。重跑同一 commit 可以得到相同素材；要重現舊素材，用 `--revision <commit>`。
- **不送任何認證。** 資料集是公開的；Python `urllib` 會把 Authorization 標頭帶到重新導向的其他網域，所以下載器刻意不支援 token。若下載被擋，手動下載三個檔案（`en_us/test.tsv`、`cmn_hans_cn/test.tsv`、`en_us/audio/test.tar.gz`），用 `--source-dir <資料夾> --revision <commit>`。
- 依**句子 ID** 配對英文音訊與中文參考，不依列號；每句只取一個錄音。
- 中文參考是簡體（`cmn_hans_cn`），另以 OpenCC `s2twp` 轉成繁體供評分；台灣用語仍需人工抽查。
- 含數字、否定、條件句的句子優先納入（約佔前 40%），並記錄涵蓋數量。
- 每句只裁去接近數位靜音的頭尾，保留低音量語音，不做音量正規化。再用固定亂數種子插入間隔：60% 是 0.15–0.45 秒（模擬連續講話），40% 是 0.9–1.6 秒（明顯停頓）；原錄音仍可能保有低音量背景聲與額外停頓。
- 輸出到 `quality/eval/`（不進 Git）：`.wav` 串流、`.reference.json`（每句時間、英文原文、簡繁中文參考、資料版本）、`.manifest.json`。

**限制：** 這是朗讀句子的人工串接，說話者切換、接點與停頓分布都不是自然直播。通過這組不代表直播品質沒退步，還需要另一組自然連續語音（例如自己錄的口語片段，人工校正逐字稿與譯文）。

### 音量變體（只改音量，其餘完全相同）

FLEURS 英文錄音音量差異很大：2026-10-24 基準的 126 句，有效語音 RMS 中位數約 −60 dBFS，88 句峰值低於 −30 dBFS（原始檔即如此，非解碼問題）。為了把「聽不聽得到小聲語音」和「斷句／顯示策略」分開量，另建一個音量正規化變體，**與原音量組一起報告**，不取代它。

```powershell
.venv-win\Scripts\python.exe windows\build_fleurs_eval.py --minutes 20 --revision 70bb2e84b976b7e960aa89f1c648e09c59f894dd --loudness-dbfs -20 --match-reference quality/eval/baseline-20261024/fleurs-en-zh-20min-seed2026.reference.json --out quality/eval/baseline-20261024-active-20dBFS
```

- **−20 dBFS 指的是「自訂有效語音 RMS 估計」**：以 20 ms 為一格算 RMS，只取比該句第 95 百分位格低不到 30 dB 的格子再算 RMS。這是本專案自訂的估計方式，**不是 ITU-T P.56 量測，也不宣稱符合該標準**。不是峰值，也不是整段 RMS，所以停頓與頭尾雜訊不會把它拉低。
- 每句只乘一個固定增益；頭尾雜訊會一起放大，句間停頓仍是數位靜音。
- 增益上限 +50 dB；若放大後峰值會超過 −1 dBFS，就降低增益（不削波、不壓縮），該句實際音量會低於 −20 並標記 `peak_limited`。近乎無聲的片段標記 `gain_capped` 或 `no_active_speech`，不會無限放大。
- `.reference.json` 每句記錄原始有效 RMS、原始峰值、增益、輸出有效 RMS、輸出峰值與上述旗標；整份記錄定義與統計。
- `--match-reference` 會比對句子 ID、順序與時間（`timeline_sha256`），不一致就中止且不寫任何檔案；既有輸出檔一律不覆寫。
- 2026-10-24 用相同快取試建：時間軸與原音量組一致；30 句因峰值上限降低增益（輸出 −25～−20 dBFS），0 句達增益上限。
- 原音量舊結果可以先和正規化結果比較；若差異明顯，應再用**目前相同程式**重跑原音量組，排除版本、快取與執行順序的干擾，再下結論。
- 這組實驗只回答「音量處理能改善哪些問題」，不能直接推論產品端應預設開啟自動增益。

## 2. 用真模型重播（每個設定跑一次）

先啟動服務並確認 `http://localhost:8787/health` 已 ready。每換一個設定都要完整重啟服務。

```powershell
# A：目前預設
$env:MOSA_EVAL_ASR="stream-en"; $env:MOSA_EVAL_OUTPUT="eval-A.json"
node windows/evaluate_live.mjs quality/eval/fleurs-en-zh-20min-seed2026.manifest.json

# B：只改一個變因，例如重啟服務前設定 MOSA_BREATH_CUT=1，再重播
$env:MOSA_EVAL_OUTPUT="eval-B.json"
node windows/evaluate_live.mjs quality/eval/fleurs-en-zh-20min-seed2026.manifest.json
```

重播以實際速度進行（20 分鐘素材約需 20 分鐘），走與擴充功能相同的 `live-client.js`，但**不含 Chrome 擷取與畫面繪製**；最後仍要做一輪真 Chrome 驗收。

## 3. 評分與比較

```powershell
.venv-win\Scripts\python.exe windows\score_eval.py quality\eval-A.json quality\eval-B.json --save quality\eval-AB-report.json
```

| 層次 | 指標 | 說明 |
|---|---|---|
| 辨識 | 整份 WER（原始／數字正規化） | 原始版照字面比；正規化版把拼寫數字轉成阿拉伯數字（three = 3、1,200 = 1200）。兩版都保留正負號與小數點（-3 ≠ 3、3.5 ≠ 3 5） |
| 翻譯 | 整份 chrF | 與分段無關；只是相似度輔助，少一個「不」幾乎不影響分數 |
| 翻譯 | 數值、正負號、否定檢查 | 只用與該句音訊**確實重疊**的字幕：檢查數值（含小數）是否遺失、辨識是否丟了負號、否定句是否缺少「不／沒／未／別／無／非」等。參考含負數時，中文正負號無法自動判定，一律列入複核。這些是**待人工複核**的標記，不是語意分數 |
| 涵蓋 | 確實覆蓋／只在邊界附近／漏句 | 字幕與參考句音訊有重疊才算覆蓋。只在 200 ms 邊界內相鄰、沒有重疊的句子列為「只在邊界」，不跑檢查、一律列入複核，不算成功 |
| 速度 | 句尾到定稿「可用」p50／p95、依斷句原因的延遲 | 用重播的音訊時鐘推算用戶端收到事件的時間，**不是觀眾在畫面上看到的時間**（不含 Chrome 擷取、訊息傳遞與繪製） |
| 預覽（旁路） | 預覽譯文比定稿早多少可用、定稿不再以第一版預覽開頭的比例 | 畫面不改；實際會看到什麼取決於顯示規則，作為之後提前顯示規則的基準 |
| 翻譯模型 | Ollama 讀提示詞與生成時間、tokens/s | 單位是 token，不是字數；只保留最近 200 次已完成的請求，長時間重播可能不涵蓋全程 |

**評分器版本 2026-10-24.2 新增：**

- 「參考音檔片段結束 → 最後相關定稿可用」：每個確實覆蓋的參考句，取與它重疊、結束最晚的定稿，用其可用時間減去參考音檔片段的結束時間。片段結尾含錄音本身的尾端環境聲，所以**這不是停句後延遲**；定稿在片段結束前就可用時會是負值，保留並計數，不截成零。**負值不代表負延遲**：通常只是定稿在參考片段尾端的背景聲結束之前就已可用。跨句定稿會同時算進它覆蓋的每一句；漏句不計入。
- 舊的「片段結尾 300 ms 內的定稿」指標保留為 legacy（2026-10-24 基準只量到 3／126 句），兩者數字不能互比。
- 參考檔有記錄音量時，另依原始有效 RMS 分三組列出 WER（同一次整份對齊後把錯誤歸到各句）。這只是相關性；音量的實際影響要用音量變體在相同句子上重跑才算數。
- 報告記錄評分器版本與時間軸指紋；比較的兩份結果時間軸不同時會警告。不同評分器版本的分數分開保存、不直接互比。

**延遲可比性檢查（評分器 2026-10-25.1 起，每一對結果都比）：** 設定差異與機器速度分開判斷。機器速度用 Ollama tokens/s 與該輪自己的 ASR 時間；若不同的設定本身會改變某個指標，就不用它（翻譯模型不同 → 不用 tokens/s；ASR 模型、裝置、ASR 模式或任何 tuning 不同 → 不用 ASR 時間）。結果分四種：

- **可比較**：設定相同、速度相近。
- **A/B（某設定）**：只有列出的設定不同，且剩下可用的速度指標相近，延遲差異可歸因於該設定；不只一個設定不同時標「confounded」，無法分開歸因。
- **機器速度不同**：可用的速度指標相差超過 10%（**經驗警戒值，不是統計檢定**）。
- **資料不足**：樣本太少，或沒有任何不受差異設定影響的速度指標。

只判斷延遲能否比較；WER、chrF、覆蓋、數字與否定標記、修譯次數照常比較。2.4 版只和第一份比、設定一不同就標不可比，連 A/B 實驗本身的延遲都無法比較，已在 2026-10-25.1 改正。例：2026-10-24 的 41462ea 重播，Ollama 54.5→37.4 tokens/s，被標為機器速度不同，當時沒有記錄 GPU 狀態，原因未確認。

要比較延遲時，建議：兩組交替重播（A、B、A、B）；每次重播前後記錄 `nvidia-smi --query-gpu=clocks.sm,temperature.gpu,utilization.gpu,power.draw --format=csv` 與正在使用 GPU 的程式；重播期間不要同時玩遊戲、播放影片或跑其他 GPU 工作。

分位數一律用 nearest-rank（第 ceil(n×q) 筆），與 `summarize_evaluation.py`、`evaluate_live.mjs` 及服務端統計相同；與其他算法的數字不要混著比較。

報告會列出需要人工複核的句子編號；把這些句子和 `.reference.json` 對照判讀，再決定品質是否可接受。若重播中曾重新連線或丟音訊，報告會警告句子對齊只是近似。

## 4. 診斷：硬切後整句只剩「chat」

2026-10-24 正規化組有 8 句定稿只剩「chat」「and chat.」或「comments」，前一句全是 6 秒硬切。其中 7 句對應的是 4.5–6 秒、正常音量的連續語音，代表整段內容被取代，不只是邊界掉字。候選原因（皆未驗證）：`asr_glossary.json` 把「Twitch」「chat」當 Whisper 提示詞造成幻聽，或硬切後的重疊去重把真正的字濾掉。

**2026-10-24 CPU 診斷結果**（`quality/level-normalized-20261024-chat-diagnosis-cpu.json`，Linux 沙箱 CPU int8；服務是 CUDA int8_float16，數值略有差異）：有提示詞時 8 句中 5 句仍輸出「chat」，與服務輸出相同；拿掉提示詞後 0 句，且 5 句都恢復成與參考原文相符的內容（例如「will be issued because the quake did not need the magnitude 6.5 requirement」）。是否過濾重疊字不影響結果；過濾掉的 3 處都是上一句帶過來的 224 ms 重疊。第 6、155 句在 CPU 上沒有重現，第 189 句只有 0.48 秒，各條件都有不同幻聽。結論：主要原因指向辨識提示詞被 Whisper 直接輸出；尚未在 GPU 上重現，修正後仍需完整基準重跑。

**修正（`MOSA_ASR_ECHO_RETRY`，預設開啟）：** 只在硬切後的片段（有重疊）、且辨識文字除了 and、oh 等虛詞外全是提示詞裡的詞時，拿掉提示詞重新辨識一次；其他解碼與重疊過濾設定不變，最多一次，重辨結果即使是空字串也採用。CPU 功能檢查：上述 5 句全部恢復，3 句不符合條件未觸發；以該輪事件估算，335 個硬切後辨識結果中會觸發 27 次（定稿 8、預覽 19）。CPU 上每次重辨約 3 秒，不代表 GPU；實際額外延遲與效果要在 Windows CUDA 上用完整基準重跑確認，目前不能宣稱已修好。

**2026-10-25 正控制結果與調整：** 合成語音正控制（`docs/codex-chat-controls-2026-10-25.md`）中，guard 開啟時 60 個樣本有 1 個真的「chat」在重試後變成「long is left.」，關閉時 0 個遺失；另有數個重試保留了 chat 但多出雜字。重試片段長度：真的 chat 0.58–1.76 秒，FLEURS 幻聽 2.34–6.14 秒。因此改為：**guard 預設關閉**；開啟時只在實際重辨音訊至少 `MOSA_ASR_ECHO_MIN_MS`（暫定 2000 ms）才重試，較短或長度未知就不重試並計入 `skipped_short`。依已存事件預測（尚未 GPU 重跑）：正控制的 18 個重試定稿全部不再觸發，只剩 1 個 2.05 秒的預覽仍會重試；FLEURS 的 7 個幻聽定稿仍會修正，3 個 1.1–1.5 秒的預覽不再重試、會短暫顯示 chat 直到定稿。2 秒是用同一批資料推得的暫定值，須以 GPU 重跑 FLEURS 與正控制確認後，才考慮恢復預設開啟。

```powershell
# 會用 GPU：先停止遊戲與其他 GPU 工作；或加 --device cpu（數值與服務的 CUDA 略有差異）
.venv-win\Scripts\python.exe windows\diagnose_chat_hallucination.py quality\level-normalized-20261024.json
```

腳本只讀取資料、不改任何設定；模型只從本機快取載入，不下載。對每句可疑定稿，從重播 WAV 切出服務當時辨識的同一段音訊，用服務完全相同的參數在四種條件下各辨識一次：有提示詞＋重疊去重（等同服務）、無提示詞、不去重、兩者皆無；並列出每個原始片段的信心值、是否被保留，以及每個字相對重疊截止點的時間。報告另存新檔。加 `--all-after-hard-cut` 可檢查所有硬切後的定稿。這是單次診斷，只能指出可能原因；任何修改仍要用完整基準重跑確認。
